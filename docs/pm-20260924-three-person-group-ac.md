# 三人共享打卡小组改造验收标准

范围：把当前固定双人打卡改为固定三人小组。保留每人独立编辑自己的模板、每日计划、打卡和留言；三位成员在同一小组内互相查看计划、进度、产出和公开留言。

## 实体与生命周期

### 打卡小组

生命周期：创建 → 已配置三名成员 → 使用中。

- 小组创建后拥有固定`id`和名称。
- 三位成员通过`group_members`关联进入小组；成员未加入小组时不能读取小组数据。
- 当前版本不提供产品内创建、退出或切换多个小组的入口，避免把这次三人扩容扩大为完整社群系统。

### 小组成员

生命周期：SupabaseAuth账号存在 → 被管理员加入小组 → 可使用产品。

- 每个成员有自己的`users`资料、模板、每日计划和留言。
- 成员只能写自己的资源；读取范围限同一小组。
- 当前版本成员关系由Supabase迁移SQL一次性配置，不通过前端邮箱搜索或公开注册自动加入。

### 计划与留言

生命周期保持现有规则：模板可编辑，每天计划从模板生成，时段可打卡和写产出，留言可发布和删除自己的。

- 每条模板、每日计划和留言增加`group_id`归属。
- 旧数据迁移时补上同一个小组归属，不复制、不删除、不重置时段状态。

## 五个必问

### 空状态

- 某成员尚未建立模板或当天计划时，该成员列显示现有对方空状态，不影响另外两人查看和打卡。
- 用户登录成功但尚未加入任何小组时，显示独立的等待加入提示，不加载或泄露其他用户数据。
- 小组少于三人时，页面显示成员未加入提示，不把空位当作真实成员。

### 失败处理

- 小组信息读取失败时，页面显示连接失败和重试入口，不渲染错误的成员列表。
- 迁移SQL找不到三名指定账号时必须中止事务，不产生半配置小组。
- 实时订阅断开时沿用现有连接断开提示；重连后按事件中的`user_id`刷新对应成员列。
- 成员打卡或编辑保存失败时，仅回滚该成员自己的乐观更新，并保留其他两人已加载状态。

### 数据引用与权限

- 模板、每日计划、留言均引用小组和资源所有者。
- 删除Auth用户仍由既有外键级联处理；本次不增加删除成员入口，避免误删计划历史。
- 所有查询通过小组成员关系收口，登录但不属于小组的账号不能读取任何成员计划或留言。

### 并发

- 三名成员可以同时打卡；每条更新根据事件中的`user_id`写入对应的成员视图。
- 同一成员多设备编辑同一天计划时沿用当前整条`slots`数组后写覆盖规则，本次不引入冲突合并。
- 留言Realtime仍按`id`去重，避免自己的乐观发布与回声事件重复显示。

### 后悔与撤销

- 保留现有取消打卡、编辑时段、删除自己留言能力。
- 不提供小组成员删除入口；成员归属调整只通过Supabase后台迁移SQL完成。
- 不删除或重建既有模板、每日计划和留言。

## 输入输出链

输入：

- SupabaseAuth会话 → 风险：无会话时跳转登录页。
- `group_members`中的当前成员归属 → 风险：没有归属时显示等待加入页。
- 小组成员资料、模板、每日计划、留言 → 风险：RLS拒绝或网络失败时显示重试状态。
- Realtime的当天计划事件和留言事件 → 风险：断开时显示重连提示，恢复后继续更新。

输出：

- 三人成员视图 → 桌面端三列，移动端三页签。
- 每日总结 → 三位成员四项指标和合并备注时间线。
- 模板、计划、留言写入 → 必须带当前小组`group_id`，并受所有者校验。
- 数据库迁移SQL → 用户在SupabaseSQL Editor执行，事务失败时不改变现有数据。

## 子功能优先级

### 必须在V1实现

1. 小组和成员关系表、资源`group_id`迁移、RLS权限收口。
2. 当前三名成员的读取、模板和每日计划按小组范围加载。
3. 三人当天计划、历史、未来预览和Realtime同步。
4. 桌面端三人布局、移动端三人页签和成员概览。
5. 三人每日总结、留言作者名称映射。
6. 旧数据安全迁移SQL和账号加入说明。

### 应该在V1实现

1. 未加入小组、成员缺少模板、小组不足三人时的明确界面。
2. 登录页对网络、账号密码、邮箱未确认提供更准确的错误提示。
3. README、CLAUDE、使用手册和WORKLOG同步更新。

### 可以延后

1. 产品内成员邀请、申请与批准流程。
2. 多个小组切换、成员退出和历史归档。
3. 四人及以上的动态成员数支持。

## 验收标准

### AC-1：三人小组迁移不丢历史

- 前置：数据库内已有两名成员的模板、每日计划和留言，第三名成员已有Auth账号。
- 操作：在SupabaseSQL Editor执行三人迁移SQL，并填入三名成员的邮箱。
- 期望：SQL事务成功；三名成员均有同一个`group_id`；旧模板、每日计划和留言保留原`id`、所有者、时段和完成状态，只新增同一个`group_id`。

### AC-2：迁移成员校验

- 前置：迁移SQL中的任意邮箱不存在或重复。
- 操作：执行迁移SQL。
- 期望：事务报错并回滚；不新建小组、不改旧数据、不出现部分成员已加入的状态。

### AC-3：小组外账号隔离

- 前置：存在一个不属于该小组的已登录账号。
- 操作：该账号调用`users`、`templates`、`day_plans`、`messages`的查询。
- 期望：查询结果不包含该小组的记录；应用显示等待加入页，不显示任何成员姓名、计划、产出或留言。

### AC-4：成员只能写自己的数据

- 前置：三名成员均已加入同一个小组。
- 操作：成员A尝试更新成员B的模板、每日计划或留言。
- 期望：SupabaseRLS拒绝写入；成员B的数据库记录不变。

### AC-5：桌面端三人计划

- 前置：三名成员均有当天计划。
- 操作：在宽度≥1200px打开当天主视图。
- 期望：显示三列等宽计划，分别标明我和两名成员；仅本人列有添加、编辑和打卡入口；每一列都显示正确的完成数、时段状态和产出记录。

### AC-6：移动端成员切换

- 前置：三名成员均有当天计划。
- 操作：在宽度＜768px打开主视图并依次点击三个成员页签或概览条。
- 期望：一次只显示被选成员的完整时段列表；三页签均不低于44px高；切换成员不改变当前日期；本人页保留编辑入口，其余成员只读。

### AC-7：三人Realtime同步

- 前置：三名成员同时打开当天页面。
- 操作：任一成员打卡、取消打卡或编辑当天时段。
- 期望：另外两人页面在Realtime事件到达后更新该成员对应列，不覆盖自己的列或第三人的列；连接断开时显示既有重连提示。

### AC-8：三人每日总结

- 前置：三名成员当天存在任意计划与打卡记录。
- 操作：打开每日总结。
- 期望：总结显示三名成员的完成率、完成数、拖延次数、拖延时长；备注按打卡时间合并成一条时间线；不展示双人专属文案或总冠军结论。

### AC-9：留言板三人显示

- 前置：三名成员均加入小组。
- 操作：任一成员发布留言。
- 期望：三名成员都能收到并看见正确作者姓名；只有作者本人可删除该留言；小组外账号看不到留言。

### AC-10：未加入小组状态

- 前置：Auth账号存在但没有`group_members`记录。
- 操作：该账号登录。
- 期望：显示等待加入小组的说明和退出登录入口；不发生空查询报错，不显示其他成员数据。

### AC-11：登录错误可辨认

- 前置：网络中断、账号密码错误、邮箱未确认分别发生。
- 操作：提交登录。
- 期望：界面分别显示网络连接异常、邮箱或密码错误、邮箱尚未确认的对应提示；不再把所有错误统一显示为邮箱或密码不对。
